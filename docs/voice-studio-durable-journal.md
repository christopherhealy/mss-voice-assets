# Studio durable HeyGen journal — disabled integration

`createVoiceStudioJournal({db, encryptionKey, keyId, profile})` implements the existing route contract using voice_text_items and voice_assets. Nothing installs it at startup. The route remains disabled. No migration, profile insert, credential or encryption key is created. Only the fixed approved synthetic Italian Julie line/profile/settings are accepted.

Identity is `studio:<cacheIdentity>`, with the exact text hash and approved profile ID. Every operation checks the QA database name and active HeyGen/Italian profile. A reviewed live connection must separately enforce destination, role, verified TLS and least privilege; this module supplies no connection string. Use an autocommit connection/pool: never retain an uncommitted dispatch claim across a provider operation. The text row is inserted with DO NOTHING, never modified on conflict. The asset unique index establishes exclusive creation of a protected pending row. A committed guarded transition marks dispatching before the caller is allowed to POST. A failed or lost acknowledgement is not permission to dispatch again.

Marker: `_voice_studio_journal_v1`. Its value is a versioned AES-256-GCM envelope with key ID, random 96-bit IV, authentication tag and ciphertext. Authenticated additional data binds application, generation key, profile ID and source hash. The plaintext inside encryption includes version, application, identity, owner token, state, accounting, provider request ID, recovery URL, duration, returned engine, requested model and byte hash when available. No recovery URL or request ID is copied to ordinary asset columns or logs. The caller must supply a reviewed 32-byte key from protected custody and retain it across restarts; missing/wrong keys, unknown versions or tampering fail closed. No key generation, Keychain access or rotation is implemented.

Transitions: pending → dispatching → generated → downloaded → stored → ready. The generated state and encrypted recovery reference are committed before audio GET. Downloaded stores the validated byte hash/length, not the audio bytes. Stored follows a private object write. Dedicated pipeline asset registration preserves the encrypted envelope and stores only the opaque internal audio reference; finish then marks ready. Dispatch failure without a recovery reference becomes uncertain; a failure with a reference becomes recoverable. Unknown outcomes never reset to pending. There is no automatic generation retry.

Each update compares ID, prior state and the complete prior encrypted envelope. It also checks the caller's journal-instance owner token. Explicit, separately server-authorized recovery may atomically take over generated/downloaded/stored/recoverable work; other states cannot be reclaimed automatically. Old owners cannot update after takeover. Interrupted pending/dispatching/recovering states require operator reconciliation and remain blocked; no lease expiry unlocks them. Recovery re-downloads existing audio and verifies a previously persisted byte hash, without another POST. An expired or lost provider URL requires operator investigation, not regeneration.

Inject journal.pipeline only into the Studio route; it never calls the ordinary upsert. It rejects public delivery URLs and out-of-context writes. The Step 263 ordinary-upsert marker guard remains unchanged, as do Live, Ingle and Fluently code paths. Object storage, authenticated playback and existing route coalescing remain separate contracts. Private-storage wiring, encryption-key custody, reviewed secure transport, profile/generation approval and verified pricing/budget authorization are still required before enabling.

Verification: mocked SQL/CAS, encrypted metadata, lost acknowledgements, new-instance recovery, no-repeat generation, private playback, and stale-owner tests. An opt-in PostgreSQL test requires a fresh owner-only /private/tmp/voiceassets-journal-pg264.* Unix-socket cluster (port 56364), never DATABASE_URL or shared QA. It creates synthetic fixture tables in a disposable local database, uses rollback-only transactions for conflict/upsert checks, and commits synthetic evidence only to verify actual cross-process recovery. The entire cluster is then stopped and deleted. This is not an application migration. No shared QA rows or sequences are changed.
